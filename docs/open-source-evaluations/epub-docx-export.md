# EPUB and DOCX export evaluation

**Decision:** use exact `docx@9.7.1` and `fflate@0.8.3` as Host-only
implementation dependencies inside the single `@novel-agent/novel-project`
plugin.

**Evidence date:** 2026-08-31

## Product boundary

The existing `publish_novel_manuscript` Tool remains the only publication
entry. It reads one accepted manuscript unit from an explicit aggregate
revision, or assembles a whole Book's Chapter manuscripts in accepted narrative
hierarchy order. It requests stock DSH approval, resolves the named target
through `ctx.fs`, optionally reads a Workspace PNG/JPEG `coverPath` for EPUB,
writes the selected format and leaves Canon unchanged. Its
stock generic call presentation declares `kind: edit` plus the destination
location, so the existing DSH Produced Files surface can list the result.

There is no second Tool, exporter package, download manager, Better Sidebar tab,
Pi TUI extension, adapter, Profile, Bundle or document settings UI. Generic
EPUB/DOCX upload and extraction remain the responsibility of the separately
installed `dsh-file-upload` plugin; novel-agent owns only accepted-revision
selection and publication.

## Why these APIs

`docx` directly maps the accepted document title, ordered Chapter headings and
manuscript lines to OOXML paragraphs and returns bytes in memory. It avoids a
Markdown intermediate, browser Blob or output-path-owned library. `fflate`
supplies the one generic primitive the EPUB format needs: deterministic ZIP
entries with the first `mimetype` entry stored without compression.
`novel-project` serializes the domain-specific EPUB 3 metadata, ordered
navigation, spine and chapter XHTML itself.

The Host build owns both imports. The client build still reports only `zod` as
a bundled dependency, so neither document library enters `conversation.view`.

## DSH seam and observed limitation

DSH `0.1.1-rc.2` publishes `resolve`, `stat`, `processPath`, `readBytes` and
text-only `writeText`; it has no binary mutation. The binary path therefore
uses the documented capability handoff:

1. stock `tools/pre-execute` approval;
2. `sandboxPolicy.resolve()` and `ctx.fs.resolve()` for the canonical target;
3. optional approved cover resolution plus `ctx.fs.readBytes()`;
4. `ctx.fs.stat()` for `create|update` receipt classification;
5. `ctx.fs.processPath()` to obtain the provider execution-world path;
6. Node `writeFile()` for the generated bytes.

This preserves DSH approval, target identity and display path. It does not pass
through the text-only `dsh-fs-sandbox.writeText/editText` mutation fence, so the
implementation and evidence do not claim binary filesystem sandbox enforcement.
Adding a wrapper cannot manufacture that missing upstream guarantee.

## Rejected candidates

- `markdown-docx@1.7.0`: capable, but adds Markdown parsing, KaTeX, image and CLI
  dependencies before ultimately calling the same `docx` Packer. Accepted Canon
  is already structured title plus text.
- `officeparser@7.8.0`: can emit EPUB bytes but does not create DOCX and brings a
  large parsing/OCR closure; File Upload already owns generic extraction.
- `epub-gen-memory@1.1.2`: memory API works, but its published tarball does not
  include a LICENSE file and its larger closure includes resource-download
  behavior that this local accepted-text path does not need.
- `wp-epub-gen@0.6.3`, `epub-gen@0.1.0`: own an output path instead of returning
  bytes and are unnecessary behind the existing DSH target seam.
- `tsepub@1.1.31`: returns a browser Blob and publishes a broken declaration path.
- `dsh-office-tools`, `dsh-univer-office`, `DSH-Office`: incompatible old DSH
  prerelease lines, excessive scope or unverifiable external licensing. They
  remain rejected downloads rather than novel-agent dependencies.

## Validation boundary

Focused RED first failed because the strict Publish request rejected `format`.
A second presenter RED proved that `kind: execute` without locations did not
join stock Produced Files. GREEN generates real EPUB/DOCX bytes, proves the EPUB
ZIP header, uncompressed first `mimetype`, container, OPF, nav and chapter, and
proves DOCX content types plus title/body in `word/document.xml`. The request
publishes an R1-sourced unit from aggregate R2 and verifies Canon remains R2.

A later whole-book RED failed because the same strict Tool request rejected
`scope` and `title`. GREEN resolves one accepted Book, walks the already ordered
Book → Volume → Arc → Chapter projection, matches each Chapter id to its
accepted manuscript and preserves every source revision. The parameterized
proof accepts Chapter B at R1 and Chapter A at R2, then verifies A-before-B in
EPUB OPF/spine/nav/XHTML and DOCX XML while Canon remains R2.

A focused whole-book DOCX RED then proved Chapter headings were contiguous with
the prior body. GREEN uses the adopted `docx` paragraph option
`pageBreakBefore: true` on each Chapter heading; unpacked OOXML proves both
chapters start a new page while order and text remain unchanged. A following
RED proved the document had no chapter navigation; GREEN adds a Word TOC field
after the title and before Chapter A with `headingStyleRange: '2-2'` and
hyperlinks, while retaining the same headings and order.

A cover RED then failed because the strict request rejected `coverPath`. GREEN
keeps the same Tool and approval, reads a Workspace PNG or JPEG through DSH fs,
preserves its bytes, adds the EPUB 3 `cover-image` manifest item and a cover
XHTML first in the spine. The parameterized integration proves `.png` and
`.jpeg` → `.jpg`, both media types, approval-before-write and unchanged Canon.
Other image/media embedding, original source bytes/BOM, production installation
and user acceptance remain outside this increment.

An EPUB metadata RED then failed because the strict request rejected `author`
and `language`. GREEN passes the optional values through the same publication
object and writes escaped `dc:creator` / `dc:language` entries in OPF. No author
store, settings UI or additional dependency was added. A following DOCX RED
observed the default `Un-named` creator; GREEN passes that same optional author
to `Document`, and unpacked `docProps/core.xml` proves the real `dc:creator`.
The same core document now also receives the already resolved publication title,
with unpacked proof for `dc:title`.

A DOCX-template RED then failed because the strict Publish request rejected
`templatePath`. GREEN reuses the already adopted `docx@9.7.1`
`patchDocument`/`PatchType` API: after stock approval, it reads one Workspace
template through DSH fs, replaces fixed `{{title}}` and `{{content}}`
placeholders with accepted-revision material, preserves the remaining template
content and reports the resolved template path. No dependency, template store,
UI or second Tool was added.

A fresh DSH `0.1.1-rc.2` Web Profile also installed and resolved the current
single plugin, started the Host, and served both the root and the unchanged
259,173-byte client artifact at HTTP `200`. This is package/load evidence; the
binary bytes and Canon invariants are proved by the focused Host integration.
